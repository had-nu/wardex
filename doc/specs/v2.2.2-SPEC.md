# Wardex v2.2.2 — Specification

**Data:** 2026-07-06
**Autor:** André Ataíde
**Base:** v2.2.0 (CPL) + v2.2.1 (state store + rejection logging) + HEAD (pathguard + usability)

---

## Contexto

v2.2.2 combina duas áreas de melhoria:

1. **Security Hardening (Cordyceps)** — 2026-06-29: Três findings de segurança da revisão pós-análise Cordyceps (CI-1, CI-2, CI-3). Supply chain fix, imagens Docker assinadas, e path traversal protection.

2. **Usability Improvements** — 2026-07-06: 8 novos comandos + 4 bug fixes para completar o workflow WF-001 (Cadeia de Evidências Criptográficas). O workflow executado com v2.2.0 revelou que 20 dos 30 comandos descritos não existem no CLI.

Ambas as áreas são backward-compatible e classificadas como melhorias, não features novas.

## P0 — Fixes (B1-B4)

### B1. `policy validate` — aceitar `.yaml`

**Problema:** `policy validate` e `policy list` procuram apenas `*.yml`. A maioria dos users usa `.yaml`.

**Ficheiro:** `internal/policy/policy.go`

**Fix:** Alterar o glob de `*.yml` para `*.{yml,yaml}`.

**Teste:**
```bash
# Criar ficheiro .yaml e validar
cp test/testdata/framework/iso27001/technological_controls.yml /tmp/test.yaml
wardex policy validate /tmp/
```

---

### B2. `art14 verify` — feedback quando falta secret

**Problema:** `wardex art14 verify <id>` crasha com erro genérico quando `WARDEX_ACCEPT_SECRET` não está definido.

**Ficheiro:** `cmd/art14/verify.go`

**Fix:** Verificar `WARDEX_ACCEPT_SECRET` antes de processar e mostrar mensagem útil:
```
Error: WARDEX_ACCEPT_SECRET is required for Art. 14 verification.
Hint: Generate a key with: openssl rand -base64 32
      Then export: export WARDEX_ACCEPT_SECRET="$(openssl rand -base64 32)"
```

---

### B3. `audit verify-chain` — flag `--session-id`

**Problema:** Múltiplas execuções de `wardex evaluate` criam entradas com chains diferentes, causando TAMPERED falso.

**Ficheiro:** `cmd/audit/verify-chain.go`

**Fix:** Adicionar flag `--session-id` para filtrar entradas da mesma sessão. Sem flag, verificar cada segmento de chain individualmente.

**Output:**
```
Audit log hash chain: VALID (3 segments, 12 entries)
  Segment 1 (session abc123): 4 entries — VALID
  Segment 2 (session def456): 5 entries — VALID
  Segment 3 (session ghi789): 3 entries — VALID
```

---

### B4. `state verify` — mensagem sem state store

**Problema:** `wardex state verify` sem state store mostra "No state recorded yet" — pouco útil.

**Ficheiro:** `cmd/state/state.go`

**Fix:** Mostrar mensagem accionável:
```
No state store found at .wardex/

To enable persistent state tracking:
  1. Add to wardex-config.yaml:
     state_store:
       enabled: true
       dir: .wardex
  2. Run: wardex evaluate --config wardex-config.yaml ...
```

## P2 — Código Novo (D1-D2, D4)

### D1. `auth status` / `auth verify`

**Comandos:**
```bash
wardex auth status --trust ./wardex-trust.yaml
wardex auth verify --trust ./wardex-trust.yaml --actor "andre.ataide@root.pt"
```

**Output (status):**
```
Trust store: ./wardex-trust.yaml
  Status: VALID
  Admin key: aa-admin-01
  Active keys: 2
  Revoked keys: 1
  Root signature: VALID
```

**Output (verify):**
```
Actor: andre.ataide@root.pt
  Key: aa-admin-01
  Role: admin
  Status: ACTIVE
  Can perform: trust.init, trust.add, config.seal, evaluate
```

**Implementação:**
- Ficheiro: `cmd/auth/status.go`, `cmd/auth/verify.go`
- `status`: wrapper de `trust.LoadStore()` + `VerifyRootSig()`
- `verify`: wrapper de `trust.ActiveKey()` + `trust.CanPerform()`
